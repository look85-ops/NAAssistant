# /code-review — Двухосевое ревью кода

Ревью изменений по двум осям: **Стандарты** и **Спецификация**.

## Когда вызывать

- Ревью ветки перед мержем
- Проверка изменений перед коммитом
- «Посмотри код» / «Проверь изменения»

## Оси ревью

### Ось 1: Стандарты
Соответствует ли код задокументированным стандартам проекта?

Проверяем:
- CODING_STANDARDS.md (если есть)
- CONTRIBUTING.md (если есть)
- Бейзлайн запахов Фаулера:
  - **Загадочное имя** — функция/переменная не раскрывает назначение
  - **Дублированный код** — одинаковая логика в разных местах
  - **Зависть к функциям** — метод лезет в данные другого объекта
  - **Кучка данных** — одни и те же поля бегают вместе
  - **Зацикленность на примитивах** — string стоит за доменным понятием
  - **Повторяющиеся свитчи** — одинаковые каскады в разных местах
  - **Хирургическая операция** — одно изменение требует правок вmany файлах
  - **Разнородное изменение** — файл правят по разным причинам
  - **Генерализация на пустом месте** — абстракция для ещё не существующих нужд
  - **Цепочки сообщений** — длинные a.b().c().d()
  - **Перекупщик** — класс делегирует дальше
  - **Отказ от наследства** — подкласс игнорует базовый

### Ось 2: Спецификация
Соответствует ли код тому, что просили?

Ищем спецификацию:
1. Ссылки на issue в коммитах (#123, Closes #45)
2. Файл-путь, переданный пользователем
3. PRD/спека в docs/, specs/, .scratch/
4. Если нет — спрашиваем где спецификация

Проверяем:
- Требования из спеки, которые отсутствуют или неполные
- Поведение, которое не просили (scope creep)
- Требования, которые «реализованы», но неправильно

## Формат вывода

```
## Стандарты
[файл:строка] Запах: [название] — [описание]
→ Рекомендация: [как исправить]

## Спецификация
[файл:строка] Требование: [цитата из спеки]
→ Статус: ✅ выполнено / ❌ отсутствует / ⚠️ неполное

## Итого
Стандарты: N находок, худшая — [запах]
Специфика: M находок, худшая — [проблема]
```
