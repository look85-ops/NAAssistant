# /tdd — Test-Driven Development

Красный → зелёный цикл. Пишем тест первым, затем код.

## Когда вызывать

- Разработка новой фичи
- Исправление бага
- Пользователь просит «сделай через TDD» или «red-green-refactor»

## Принципы

### Хороший тест
- Тестирует поведение через публичный интерфейс, не реализацию
- Читается как спецификация: «пользователь может сделать X при условии Y»
- Не ломается при рефакторинге, если поведение не изменилось

### Швы (Seams) — где тесты живут
**Шов** — публичная граница, по которой тестируем. Тесты живут на швах, не внутри реализации.

Перед любым тестом: «Какой публичный интерфейс? Какие швы тестируем?»

### Антипаттерны
- **Зависимость от реализации** — мокаем внутренности, тестируем приватные методы. Тест ломается при рефакторинге.
- **Тавтологический тест** — assertion пересчитывает ожидаемое тем же способом, что и код. Проходит всегда.
- **Горизонтальное срезание** — пишем все тесты, потом весь код. Тестируем воображаемое поведение.

### Правила цикла
1. **Красный перед зелёным** — сначала падающий тест, потом минимальный код для прохождения
2. **Один срез за раз** — один шов, один тест, одна минимальная реализация
3. **Рефакторинг — не часть цикла** — онbelongs to review, не к red-green

## Формат вывода

```
### Цикл N
Тест: [название теста]
Ожидание: [что проверяем]
Результат: ✅ красный → ✅ зелёный
Следующий шаг: [что делать дальше]
```
