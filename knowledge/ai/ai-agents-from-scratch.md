## Главная идея туториала

Собрать агента без фреймворков, на локальных LLM, чтобы понять что под капотом.
Формула агента: **LLM + System Prompt + Tools + Memory + Reasoning Pattern**

---

## 15 шагов — от сырой LLM к production-паттернам

### 1–6: Основы LLM (фундамент, не агенты)

| Шаг | Что поняли |
|---|---|
| **Intro** | Модель загружается из GGUF-файла, создаётся контекст (рабочая память), каждый промпт — независимый вызов. Без контекста модель не помнит предыдущий вопрос. |
| **OpenAI Intro** | Альтернатива локальным моделям — API. Плюс: не грузит RAM. Минус: платишь за токены, данные уходят наружу. |
| **Translation** | System prompt задаёт роль. «Ты — хронолог, переводи время в 24-часовой формат» → модель ведёт себя как специалист, а не универсальный помощник. |
| **Think** | Модель может рассуждать, но ошибается в вычислениях. Вывод: LLM — не калькулятор, для точных операций нужны инструменты. |
| **Batch** | Параллельная обработка нескольких запросов. Важно для продакшна, но к агентности отношения не имеет. |
| **Coding** | Стриминг ответов (токен за токеном). Пользователь видит прогресс, а не ждёт полный ответ. |

### 7–15: Агентные паттерны (ядро туториала)

#### 7. Simple Agent — Function Calling (Tools)

**Это и есть рождение агента.** LLM получает список доступных функций с описанием и JSON Schema параметров. Модель сама решает, когда вызвать инструмент.

```
User: "Какое время?"
LLM: [видит функцию getCurrentTime] → вызывает → получает "14:30" → отвечает
```

Без function calling — просто генератор текста. С ним — система, способная действовать.

#### 8. Memory Agent — Постоянная память

Память хранится в JSON-файле. Менеджер памяти загружает факты и предпочтения при старте, добавляет их в system prompt. Агент сам решает, что сохранить через инструмент `saveMemory()`.

Типы памяти: **facts** (имя, город), **preferences** (любимая еда, формат ответа).

Проблемы: раздувание памяти со временем, конфликтующие данные, приватность.

#### 9. ReAct — Reason + Act (ключевой паттерн)

Цикл: **Thought → Action → Observation → (повтор) → Answer**

```
Thought: Мне нужно сложить 15 и 7
Action: add(15, 7)
Observation: 22
Thought: Теперь умножить на 3
Action: multiply(22, 3)
Observation: 66
Answer: 66
```

- Модель **думает вслух** (Thought), **вызывает инструмент** (Action), **читает результат** (Observation)
- Защита от бесконечного цикла: `maxIterations`
- Ответ детектится по ключевому слову "Answer:"
- Основа LangChain, AutoGPT, BabyAGI и всех современных фреймворков

#### 10. AoT — Atom of Thought («SQL для рассуждений»)

Принципиальное отличие от ReAct: **LLM только планирует, код — исполняет.**

```
ReAct:  LLM думает → LLM действует → LLM думает → ... (чёрный ящик)
AoT:    LLM строит план (JSON) → Валидатор проверяет → Исполнитель запускает (белый ящик)
```

Атом — минимальная неделимая операция. У каждого атома: id, тип (tool/decision/final), входные данные, зависимости от других атомов (dependsOn). План — направленный ацикличный граф (DAG).

Плюсы: воспроизводимость, аудит каждого шага, перезапуск с любого атома при ошибке.
Минус: не подходит для творческих/открытых задач.

#### 11. Error Handling — Устойчивость агента

Стандартизированная таксономия ошибок:
- **ValidationError** — кривой ввод, не повторять
- **LLMCallError** — модель упала, можно повторить
- **ToolExecutionError** — инструмент сломался, иногда можно повторить
- **AgentWorkflowError** — оркестрационный сбой всей цепочки

Стратегии: таймауты → retry с backoff/jitter → fallback (запасной инструмент) → degraded mode (без LLM) → graceful failure (понятное сообщение + correlation id)

#### 12. Tree of Thought — Поиск по дереву гипотез

**Branch → Score → Prune → Conclude**

Строим несколько гипотез (веток), оцениваем каждую числом, оставляем лучшую, отбрасываем остальные.

Применение: когда нужно **одно решение** и время ограничено. Инцидент на проде — какая причина вероятнее? Один путь исправления.

Минус: информация из отброшенных веток теряется безвозвратно.

#### 13. Graph of Thought — Граф вместо дерева

**Branch → Score → Contrast → Refine → Aggregate → Conclude**

В отличие от ToT — слабые ветки не отбрасываются. Вместо этого:
- **Contrast**: сравниваем противоречащие гипотезы, извлекаем инсайт из разногласий
- **Refine**: улучшаем слабую гипотезу с помощью сильной
- **Aggregate**: синтезируем несколько веток в одну

Применение: когда проблема **неоднозначна** и слабый сигнал может стать ключевым. Сложный баг, многофакторный инцидент.

#### 14. Chain of Thought — Аудируемая цепочка решений

Пять фаз для высокоставочных решений:
1. **Facts** — только факты, без суждений (предотвращает раннюю предвзятость)
2. **Red Flags** — явные риски по чек-листу
3. **Legitimacy** — аргументы в пользу клиента (баланс, а не однобокое подозрение)
4. **Policy Check** — бизнес-правила
5. **Decision** — решение только после всех фаз

Важно: CoT и reasoning-модели (o3, DeepSeek-R1) решают **разные** задачи. Reasoning улучшает качество ответа. CoT делает процесс **управляемым и аудируемым**. Для высоких ставок нужно и то, и другое.

#### 15. Tool Routing — RAG для инструментов

Проблема: когда у агента 80+ инструментов, каждый вызов тащит все 80 схем в промпт (тысячи токенов шума).

Решение: эмбеддинг-модель (bge-small-en) считает косинусное сходство между запросом пользователя и образцовыми фразами (exemplars) для каждого инструмента. В промпт попадают только top-k релевантных.

Это буквально RAG, но для инструментов вместо документов.

## Что применимо к NM.ASSISTANT

### Уже используем (осознанно или нет)

- **Function Calling** — каждый субагент в `.opencode/` по сути набор инструментов
- **System Prompt** — AGENTS.md, манифест, роли агентов
- **ReAct** — наши агенты думают → действуют → наблюдают, особенно career-architect и product-analyst
- **Error Handling** — guardrails в AGENTS.md (проверки перед коммитом, валидация)
- **Memory** — 3-tier memory policy (knowledge/, logs/decisions.md, BACKLOG.md)

### Можно внедрить

- **AoT** — для бустера методиста: вместо того чтобы LLM свободно генерировал сценарий, пусть строит атомарный план (модуль → тема → активность), а код детерминированно собирает HTML/документ
- **Chain of Thought** — для AOS-отчётов: факты → метрики → выводы → рекомендации (сейчас это делается, но без формальной структуры фаз)
- **Tool Routing** — когда количество команд/skills вырастет за пределы ~15, фильтровать по эмбеддингам вместо перебора всех

### Не нужно

- **Tree of Thought** — наша система не принимает решения с отбрасыванием альтернатив
- **Graph of Thought** — избыточно для текущих задач, нет неоднозначных проблем такого класса
- **Batch/Streaming/Coding** — это детали реализации node-llama-cpp, к нашей архитектуре не относятся

## Ключевой инсайт

Агент — не магия. Это **LLM + чёткий контракт**:
1. Системный промпт задаёт роль и формат ответа
2. Инструменты описаны с JSON Schema — модель знает что можно, а что нет
3. Петля ReAct/AoT даёт структуру многошаговым задачам
4. Память делает агента не амнезиком
5. Обработка ошибок не даёт упасть молча

Чем жёстче контракт (JSON вместо текста, атомы вместо свободного плана), тем надёжнее агент в продакшне.
