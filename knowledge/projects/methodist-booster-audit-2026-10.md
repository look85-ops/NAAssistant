# Аудит Бустера методиста — 2026-10-02

## Вывод

Бустер уже содержит сильную методическую основу: аудит запроса, мастер видения, генератор активностей, фасилитационные карты и симулятор учебного дня. Главный продуктовый разрыв — интерфейс в основном выдаёт ответ, но не проводит пользователя через полный verification loop:

> ответ → проверка → объяснение → следующее действие

Следующий этап развития — не «ещё один генератор», а помощники, которые помогают методисту точнее проходить этапы разработки программы и согласования.

## Подтверждённые находки

### P0 — безопасность вывода

Пользовательский текст и ответ AI вставляются через `innerHTML` без экранирования: `js/audit.js`, `js/vision.js`, `js/activities.js`, `js/ivanov.js`. Это создаёт XSS-риск для текста из полей, AI-ответов и данных, которые попадут в шаблон.

Действие: ввести общий `escapeHtml`, не вставлять пользовательский и AI-текст как HTML; для форматирования использовать безопасный renderer или `textContent`.

### P1 — AI-режим не прозрачен

На GitHub Pages функции `/functions/chat` и `/api/chat` недоступны в текущем статическом деплое. «Активности» честно показывают fallback, но «Видение» и другие страницы не дают единого ясного режима работы и источника результата.

Действие: обозначить режим на каждой AI-функции: `AI`, `проверенная база` или `локальная логика`; показывать причину fallback и ограничения результата.

### P1 — нет общего verification loop

«Видение» проверяет текстовые признаки, а «Аудит» выдаёт вердикт, но результат не содержит единой проверки источников, допущений, уверенности и следующего действия. AI-активность выводится как готовый ответ без проверки соответствия цели, времени и формату.

Действие: определить общий контракт результата: вывод, что проверено, что неизвестно, риски, следующий шаг. Для генераторов добавить второй проход проверки по входному брифу.

### P1 — нет измерения эффекта

Инструменты предлагают решения, но не возвращают к замеру: сколько итераций согласования, сколько времени заняло, что изменилось в качестве или переносе. Без этого Бустер остаётся полезной витриной, но не доказывает impact.

Действие: добавить режим «до / после» и минимальный журнал результата для одного рабочего кейса.

### P2 — мастер позволяет пройти дальше с неполными данными

В `audit.html` кнопки перехода не валидируют обязательные поля. В `vision.js` проверяется только минимальная длина текущего шага. Это позволяет получить убедительный, но слабый результат из неполного брифа.

Действие: валидировать поля перед переходом, показывать конкретно, чего не хватает, не использовать только placeholder как инструкцию.

### P2 — доступность форм и динамических результатов

Textarea и select в мастерах не имеют явных `label`; динамические блоки результата не имеют `aria-live`; скрытие шагов не сопровождается `aria-hidden` и возвратом фокуса. Пользователю клавиатуры и скринридера трудно понять, где он находится.

Действие: добавить label/fieldset, `aria-current` для шага, `aria-live="polite"` для результата и управляемый фокус после перехода.

### P2 — канонический URL и метаданные расходятся

В `methodist-booster/index.html` canonical указывает на `/metod_buster/`, а README и рабочая структура используют `/NAAssistant/methodist-booster/`. В Twitter-описании главной страницы указано «пять инструментов», хотя перечислено шесть.

Действие: выбрать один канонический URL и синхронизировать title, description, Open Graph, Twitter и Schema.org на всех страницах.

### P2 — интерфейс перегружен inline-стилями и разными визуальными правилами

Главная тема вынесена в tokens.css, но страницы и JS содержат много inline-цветов, отступов, радиусов и градиентов. Это затрудняет единый verification UI и дальнейшее развитие помощников.

Действие: вынести состояния результата, кнопки, подсказки, ошибки и источники в общие CSS-классы и токены.

### P3 — следующий шаг не является частью результата

После результата пользователь получает ссылки на другие инструменты, но не получает персонального действия: что проверить, с кем согласовать, какой артефакт сохранить и когда вернуться.

Действие: в каждом инструменте добавить блок «Следующий шаг» с одним действием, сроком и критерием готовности.

## Что работает хорошо

- Сильная методическая логика «обучение не лечит системную проблему» в `audit.js`.
- В «Видении» различены пользователь и заказчик, есть JTBD, альтернативы, MVP и критерий успеха.
- У «Активностей» есть fallback на проверенную статическую базу.
- Есть единые design tokens, focus-ring, responsive breakpoints и понятная навигация.
- Содержательно Бустер уже движется в сторону performance consulting, а не фабрики учебного контента.

4. Добавить замер результата на одном кейсе согласования.
5. Исправить валидацию и доступность мастеров.
