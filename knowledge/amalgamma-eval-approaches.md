# Eval-подходы для Амальгаммы (из awesome-evals)

Источник: github.com/benchflow-ai/awesome-evals (443+ ссылок, 146 нот, Patterns.md с кодом)

## 5 ключевых паттернов (от простого к сложному)

### 1. Code-based assertions — самые дешёвые проверки
Детерминированные проверки, которые можно написать сразу: JSON-schema, отсутствие плейсхолдеров, проверка состояния БД/файлов.
- **Когда:** ошибка проверяется парой строк кода
- **Затраты:** почти ноль
- **Для Амальгаммы:** проверка, что агент действительно создал артефакт (файл, коммит), а не только сказал «сделано»

### 2. Error analysis (open → axial coding) — понять, что реально ломается
1. Взять 30-100 реальных трейсов агентов
2. Один эксперт пишет свободные заметки — **что** пошло не так (open codes)
3. LLM группирует заметки в 4-8 категорий (axial codes) — человек проверяет
4. Приоритет = частота × серьёзность
5. На каждую топ-категорию — один узкий бинарный eval

**Для Амальгаммы:** запустить цикл Амальгаммы, собрать логи агентов, найти типовые сбои.

### 3. LLM-as-judge (бинарный, с человеческими примерами)
- Только **PASS/FAIL** (никаких 1-5 — шум между 3 и 4)
- Сигнал — в few-shot critique-примерах от эксперта, а не в длинной рубрике
- Валидация: **TPR и TNR** отдельно, а не raw agreement (на редких ошибках agreement врёт)
- Перепроверять при каждом изменении агента/промпта/данных

### 4. pass@k vs pass^k — два разных вопроса
| Метрика | Вопрос | Когда растёт k |
|---|---|---|
| pass@k | «Сможет ли хоть раз?» (capability) | Растёт → 1.0 |
| pass^k | «Сделает ли каждый раз?» (reliability) | Падает → 0 |

- pass@k — несмещённая оценка через `1 - C(n-c,k)/C(n,k)` в численно стабильной форме (произведение, а не биномы)
- **Для Амальгаммы:** pass^k важнее — агент должен стабильно делать своё дело

### 5. Outcome/state grading — проверять мир, а не слова
Агент может сказать «готово», но ничего не сделать. Правильная проверка — снэпшот состояния до/после + diff.
- Проверять и expected (изменения сделаны) И unexpected (побочный ущерб)
- Golden state = проигрывание эталонного решения на свежих данных

**Для Амальгаммы:** после каждого цикла — хэш состояния репозитория/файлов, а не лога агента.

## Что внедрить прямо сейчас

1. **CI gating** — каждый зафиксированный баг → новый тест-кейс в регрессионном наборе. Набор растёт монотонно.
2. **Бинарные проверки** — на первые топ-3 ошибки (из error analysis) написать по одному binary judge c few-shot.
3. **state_check** — вместо «агент сказал, что создал пост» → проверка, что файл реально появился в репозитории.
4. **verifiable reward** — одну и ту же rubric использовать и для eval, и для RL-тренировки (если дойдём до RL).
